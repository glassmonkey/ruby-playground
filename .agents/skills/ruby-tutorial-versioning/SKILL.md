# Ruby tutorial versioning

Follow [release discovery and verification](references/release-process.md). Discover the actual registry, loader, selection policy, resolver and publication consumers. Separate registration, runnable environment, course readiness and default selection. Do not interpret a request to update latest as permission to replace an existing default policy.

Inspect the current [data contract](../ruby-tutorial-authoring/references/data-contract.md) and [source standards](../ruby-tutorial-authoring/references/sources.md). Resolve inherited lessons under the implementation's actual merge rules, then verify claims, Example/Experiments, expected outputs, stdlib availability and official links in the bundled WASM. Preserve code whitespace and stable identities. Make development status visible in page and social metadata.

When release changes are authorized, update required registry/dependency/loader integration and necessary lesson variants. Use [authoring](../ruby-tutorial-authoring/SKILL.md) for substantial lesson writing and [curriculum](../ruby-tutorial-curriculum/SKILL.md) only if learning goals or placement genuinely change. Use [page generation](../ruby-tutorial-authoring/references/page-generation.md) for output verification; do not duplicate generation logic.

Deliver affected versions, concrete runtime evidence, content changes, readiness gaps and default/publication consequences separately. Generation or typecheck success alone does not prove compatibility. Respect the user's publication scope and report unverified checks rather than guessing results.
