# Render pages from lesson data

Inputs are `src/tutorial/data/lessons.json`, the shared chapter and redirect data, `src/versions.ts`, and the common React UI in `src/tutorial/components/` and `src/tutorial/app.tsx`. `src/tutorial/content.ts` resolves version variants; `src/tutorial/references.ts` resolves official links. The Vite plugin in `src/build/tutorial-plugin.ts` renders the same components for static SEO pages and bundles their browser application through the shared root entry. Generated HTML belongs to build output, not tracked source.

1. Check the data-stage handoff and run `npm run tutorial:validate`. Correct factual or teaching defects in lesson JSON before rendering.
2. Run the existing `npm run build` to render and bundle production pages into `public/`. There is no separate tutorial entry, generation command or prebuild pipeline. Rendering must not paraphrase or add claims; it is not a second LLM authoring step.
3. For changed lessons, run relevant `e2e/seo.spec.ts` cases against production preview. Verify static content, canonical URLs, redirects, sitemap, navigation, official references and JavaScript-disabled readability. Test aliases with a query and section fragment as well as a bare URL; a development HTTP redirect does not establish how the generated static redirect behaves. Repeat against `E2E_DEV_SERVER=1` when routing or dev integration changes. Request `/sitemap.xml` directly in development and production: verify an XML media type and body, canonical-only URLs, and no application HTML fallback. Choose a free `PORT`; do not run suites concurrently against the same output directory.
4. Open the actual preview route. Confirm course content, selected version and runtime agree; execute Example and each Experiment in the bundled WASM runtime for every supported variant. Check independent sample drafts, nearby navigation and full Playground handoff. For UI changes, inspect desktop/mobile and both themes, including theme persistence with edited code.
5. Report source changes, actual runtime versions/output, content/reference findings, checks and remaining limits. Commit or publish only when authorized; do not track build output or patch generated HTML.

The common renderer owns layout, escaping, header controls, sidebar, references and previous/next links. Render basic Example and named application Experiments, with results obtained only by Run. Omit answer disclosures, author-only completeness notes and progress controls. SEO metadata and JSON-LD must derive from the same source and describe visible content. A content-only change should not fork shared UI per lesson.

## Social images

Every available course and lesson gets a 1200×630 PNG at its canonical path plus `og.png`. `src/tutorial/social-image.tsx` uses resolved JSON (`title`, `code`), the concrete Ruby version, the shared Ruby mark/design tokens and bundled font. Version overrides must be resolved before rendering. The normal Vite build writes the PNGs; development serves them from the same renderer. The card prominently labels RUBY TUTORIAL and depicts a code editor with a Run button to communicate browser-based practice. Show the basic Example code, visibly truncate excerpts, and do not print execution results. No manually authored per-lesson image or extra JSON image field is needed.

Use the shared release label in search/social titles, descriptions, image alt text and the PNG badge. Development status must remain visible outside the page itself; inspect both a development course and a lesson card, including the longer badge's fit.

After changing image content or rendering, run the social-image unit tests and the `every tutorial article` SEO browser test in both dev and production. Check each canonical is unique and self-referencing, `og:image` and `twitter:image` are absolute URLs to a valid PNG, and `twitter:card` has a single large-image value. Inspect representative PNGs visually, including the longest title/code and a version variant; ensure wrapping/truncation keeps text clear of the footer. Keep image files in build output only.
