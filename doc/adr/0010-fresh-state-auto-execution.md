# ADR-0010: Web Worker内で、毎回まっさらな状態から自動実行する

## Status

Accepted (2026-08-22)

## Context

複数回のコード実行間で、変数・メソッド定義などの状態を持続させるか (IRB的な永続REPL状態)、それとも毎回まっさらな状態から実行するかを検討した。判断軸として次の2本を設定した:

- **決定性**: 同じsnippetのコードを、誰が・いつ実行しても同じ結果になるか
- **応答性**: 実行1回ごとの体感速度

当初、「まっさらな状態を実現するにはWASM Rubyランタイムの再作成が必要で、これは重い処理になり応答性を損なう」という懸念から、状態持続案を優先候補としていた。

その後、user自身が過去に作成・公開しているPHPの同種プロダクト ([php-play.dev](https://php-play.dev) / [glassmonkey/php-playground](https://github.com/glassmonkey/php-playground)) のソースコードを調査した。実装事実:

- `client.ts` の `runPHPInWorker` は実行のたびに `terminateWorker()` → `initializeWorker()` を呼び、Web Worker (＝WASM VM) を完全に破棄・再作成している
- 実行トリガーは明示的なボタンではなく、`editor.tsx` でコード変更を300msデバウンスした自動実行
- この「Worker毎回再生成 + 自動実行」の組み合わせで、実際に「リアルタイム」として成立し公開されている

この実例により、「VM再作成は重すぎて応答性を損なう」という当初の懸念は否定された。

また、共有されたsnippetを別のvisitorが開く場合、それは新しいブラウザタブ = 新しいWASM VMインスタンスであるため、「visitor間で実行結果がブレる」という決定性の懸念は状態持続の設定に関わらず自然に解消されることも判明した。残るリスクは「作者が自分の作業セッション中に積み上げた状態に無自覚に依存したsnippetを、そのまま共有してしまう」という自己責任の範囲に限られる。

## Decision

php-playgroundと同じパターンを採用する。

- コード実行はWeb Worker内で行う
- 実行のたびにWorkerを`terminate()`して`ruby.wasm`のVMを作り直し、現在のコードバッファ全体をまっさらな状態から再実行する
- 実行トリガーはコード変更を検知したデバウンス (300ms目安) による自動実行とする。明示的な実行ボタンは必須としない
- Web Workerを使うことで、暴走コード (無限ループ等) が発生した場合も`terminate()`で強制停止でき、メインスレッド (UI) がフリーズすることを防ぐ

## Consequences

- 決定性が高く保たれる (snippetの見た目のコードだけで結果が決まる)
- 応答性への懸念は実例により否定されたが、実装時に自分の環境でも体感速度を確認する
- Web Workerとのメッセージパッシングによる実装 (`terminate`/再初期化のライフサイクル管理) が必要になる
