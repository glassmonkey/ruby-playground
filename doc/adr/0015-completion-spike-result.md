# ADR-0015: ライブVM反射問い合わせによるコード補完は見送り、素の単語補完に倒す

## Status

Accepted (2026-08-22)

## Context

[issue #13](https://github.com/glassmonkey/ruby-playground/issues/13) のspike (time-box目安1日) として、実行用Worker (ADR-0010) とは別に、terminateしない補完専用の永続Workerを立て、カーソル位置の「レシーバ式 + 部分的なメソッド名」をライブ`ruby.wasm` VMに反射的に問い合わせて`receiver.methods.grep(/^prefix/)`のように補完候補を得る方式の実現可能性を検証した。検証したのは次の3点。

### 検証1: レシーバ式+部分メソッド名のパース精度 (事実)

- 当初`Ripper`の利用を想定していたが、実際にビルドされている`ruby.wasm` (`@ruby/4.0-wasm-wasi` 2.10.1) では`Ripper.lex`/`Ripper.sexp`等のコアメソッドが未実装 (`Ripper.singleton_methods`は`dedent_string`/`lex_state_name`のみ) で、Ripperベースの構文解析は使用不可だった。
- 代わりに`RubyVM::AbstractSyntaxTree.parse`が利用できた。「バッファ全体を直接パース → 失敗時は末尾のバランス走査で候補式を切り出し再パース」という2段構えのフォールバックを実装し、実ブラウザ上のVMで以下を検証した:
  - 単純呼び出し、メソッドチェーン、文字列/Hash/Range/添字/括弧レシーバ、名前空間定数レシーバ
  - 複数行にまたがるメソッドチェーン、複数文からなるバッファの末尾文抽出
  - `def`/ブロック/`if`の中にカーソルがあるケース (`end`や閉じ括弧が未入力の「タイピング中」の構文も含む)
  - `.`直後で部分メソッド名が空文字のケース (ダミー識別子suffixの付与で回避可能)
- 全ケースで正しくレシーバ式のソース文字列と部分メソッド名を抽出できた。「レシーバ.部分メソッド名」パターンに該当しないカーソル位置 (引数リストの途中など) は「補完トリガー対象外」と正しく判定できた。
- → 実用的な精度で抽出できることを確認した。

### 検証2: 補完専用永続Workerのレイテンシ (事実)

- 補完専用の永続Worker (VMを初回メッセージ時に1回だけ初期化し、以降使い回す) を実装し、実ブラウザ (Chrome、ローカルRailsサーバーが配信するビルド済み資産) で計測した。
- 初回起動 (fetch + `WebAssembly.compile` + VM初期化) は約880ms。永続Workerとして1回だけ払うコスト。
- ウォーム状態でのフルパイプライン (バッファ全体をASTパース → レシーバ直前までのコードを再実行 → `receiver.methods.grep(prefix)`) は、50行程度のバッファに対して平均4〜7ms、最大でも30ms未満だった。
- 比較として、既存の実行用Worker (ADR-0010のterminate/recreateパターン) のコールドスタートは約380ms/回であり、これは既にphp-playgroundの実例で「体感速度に問題ない」と判定されている水準。永続Workerのウォームレイテンシはそれよりさらに大幅に高速。
- → タイピング中の補完として許容できる速度であることを確認した。

### 検証3: レシーバ式評価の副作用リスク (事実)

- 検証2の過程で、「レシーバ式単体をeval」するだけでは、それより前のコードで定義されたローカル変数を参照できずNameErrorになることが判明した。これに対応するには「カーソルより前のコード全体を補完問い合わせのたびに再実行してからレシーバ式を評価する」設計が必須と分かった。
- この設計の帰結として、以下を実機で実証した:
  1. VM内のグローバル状態は補完問い合わせのたびに変化しうる。ユーザーが一切タイプしていない状態で同じ補完クエリを5回連続実行しただけで、グローバル変数の値が6→7→8→9→10と単調増加する挙動を確認した。これはADR-0010が定めた「決定性」原則に、実行トリガーではなく補完トリガーの経路から違反を持ち込む。
  2. **前段コードに無限ループが含まれる場合 (タイピング中には頻繁に起こりうる一時的な状態)、補完クエリが永久にハングすることを実証した。** 3秒待っても応答が返らず、その後の無関係なクエリ (`1+1`) を同じWorkerに投げても同様にハングしたままだった。復旧には`worker.terminate()`による強制終了が必要で、その場合は検証2で計測した約880msの再初期化コストが再発生する。
  3. WASIサンドボックスの外 (実ファイルシステム・実ネットワーク・実OSプロセス) への実害は確認されなかった (`File.write`→`Errno::ENOENT`、`TCPSocket.new`→`LoadError`、`system`→`pid -1`のダミー実装)。これはADR-0009の「ブラウザ内で完結、サーバーには送られない」という前提と一致しており、この意味でのリスクは低い。

### 3点の相互依存 (事実からの推論)

検証3-2の無限ループハングへの対策 (タイムアウト検出+自動recreate等) を講じようとすると、対策が発動するたびに検証2で「タイピング中の補完として許容できる」と判定した880ms相当のコストが再発生する。つまり副作用対策はレイテンシ面の優位性を部分的に打ち消す関係にあり、issue本文が想定していた「3点はそれぞれ独立に判定できる」という前提を超えて、3点が互いに絡み合っていることがspikeで判明した。

## Decision

issueの成功/失敗判定基準に照らし、**失敗**と判定する。理由:

- 検証1 (パース精度) と検証2 (レイテンシ) は単体では実用的な水準をクリアした。
- しかし検証3で見つかった「前段コードの無限ループによる永続Workerの無期限ハング」は、タイピング中に構造的に起こりやすいシナリオであり、個人利用スコープでも「補完エンジンとして機能しなくなる」という軽微でない失敗モードである。対策 (タイムアウト+recreate) を講じると検証2のレイテンシ上の優位性を再び失うため、副作用リスクはレイテンシ・精度の問題と地続きであり、time-box (1日) の範囲を超えて無限ループ検出のような本質的に難しい問題への対応が必要になる。
- よって、#9 (エディタ置き換え) のスコープにライブVM反射問い合わせ方式の補完機能は組み込まず、素の単語補完 (#9のスコープ内、追加実装なし) に倒す。

## Consequences

- #9の実装スコープに「ライブVM反射問い合わせによる補完」は含めない。エディタが標準で提供する単語補完 (バッファ中に出現済みのトークンからの補完) で十分とする。
- 本spikeで判明した事実 (Ripperが`ruby.wasm`で使用不可、`RubyVM::AbstractSyntaxTree`は利用可能、ウォームレイテンシは数ms〜十数ms) は、将来同種の検証をやり直す際の出発点として本ADRに残す。
- 将来「無限ループ検出」または「前段コードを再実行せずに安全にレシーバを評価する」設計上のブレークスルーがあれば、本判定を覆して再検討する余地はある (本ADRはその時点でSupersededとする)。
- spikeの実験コードは `frontend/src/completion-worker.spike.js` として最小限の証跡を残す。本実装ではないため、#9のスコープ確定後は削除してよい。
